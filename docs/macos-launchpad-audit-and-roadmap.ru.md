# Return Launchpad: аудит и план доработки

Дата: 10 сентября 2026 года. Исходная ревизия: `2caf4d9` (`v2 release`).

## Вывод

Приложение уже нативное: Swift + SwiftUI, с AppKit для окна, размытия, ввода и запуска приложений. Менять весь стек не требуется. Основные проблемы находятся в синхронной загрузке каталога, жизненном цикле процесса и незавершённой модели взаимодействия с сеткой. Анимационная библиотека сама по себе их не исправит.

Из описания пользователя выделены пять направлений: скорость открытия, системные приложения, папки, анимации и перетаскивание, включая переход между страницами. Ниже приведены причины, конкретные места в коде, рекомендуемое поведение и проверяемый план реализации.

Это аудит и проект решения. Код приложения в рамках исследования не изменялся. Подтверждённые свойства исходников отделены от гипотез о производительности и предложений для будущей версии.

## 1. Что сейчас есть в проекте

| Часть | Текущая реализация |
| --- | --- |
| Сборка | Xcode-проект, Swift language mode 5.0, deployment target macOS 15.5 |
| Интерфейс | SwiftUI; сетка вручную составлена из `VStack` / `HStack` |
| Интеграция macOS | AppKit: `NSWorkspace`, `NSWindow`, `NSVisualEffectView`, собственные `NSTextField` / `NSView` |
| Каталог | `AppScanner` внутри `AppInfo.swift`, синхронный обход двух директорий |

| Зависимости | В проекте нет подключённых продуктов Swift Package Manager |

Основные точки входа: `Return_LaunchpadApp.swift` создаёт `AppManager`; `ContentView.swift` содержит интерфейс, настройку окна, пагинацию и оба drop delegate. `AppInfo.swift` одновременно описывает приложение, сериализацию и сканирование. Папки в README отмечены как будущая функция.

Номера строк далее относятся к исходной ревизии и могут измениться после реализации. Пути указаны относительно корня репозитория.

## 2. Карта проблем

### 2.1. Задержки при открытии

**Подтверждено исходниками:**

- `Return Launchpad/AppManager.swift:19–44`: инициализатор вызывает `loadApps()`, который синхронно выполняет `scanApps()` и сортировку. `DispatchQueue.main.async` используется только для публикации уже готового результата; сканирование он в фон не переносит.
- `Return Launchpad/AppInfo.swift:83–117`: для каждого приложения читаются bundle-метаданные и загружается `NSImage`. Каталог и иконки готовятся вместе до появления результата.
- `Return Launchpad/ContentView.swift:40–45,97–99,166–171,401–405`: клик по фону, Escape и запуск приложения вызывают `terminate`. Следующее открытие требует нового процесса и повторной загрузки каталога.
- `Return Launchpad/AppOrderManager.swift:162–169,322–344`: порядок заново декодируется при чтении вычисляемого свойства; пользовательская сортировка повторяет линейные поиски и удаления из массива. На большом каталоге это лишняя работа.
- `Return Launchpad/PersistenceLogger.swift:60–85`: сообщения одновременно форматируются для Logger и печатаются в консоль. `AppOrderManager` также сохраняет данные по таймеру каждые 30 секунд, даже без изменений.

**Степень уверенности:** блокирующая последовательность загрузки и повторный холодный запуск подтверждены. Сколько миллисекунд занимают сканирование, декодирование иконок, сортировка и размытие, пока не измерено. Называть конкретный компонент главным потребителем CPU без Instruments нельзя.

**Решение:** быстрый показ сохранённого каталога; фоновое обновление метаданных; отдельный ограниченный кэш иконок, приоритет первой страницы. Скрывать окно после использования, сохраняя процесс; настоящее завершение оставить отдельной командой Quit. Поддержать повторное открытие из Dock и восстановление фокуса. Когда окно скрыто, остановить анимации и служебные таймеры.

Файловую работу выполнять в отдельном исполнителе, UI-состояние — на `MainActor`. Простое оборачивание в `Task {}` не гарантирует ухода с главного актора. Через границы concurrency передавать подходящие значения метаданных, а работу с AppKit-объектами проектировать с учётом изоляции конкретных API. Это соответствует разбору Apple: [Explore concurrency in SwiftUI](https://developer.apple.com/videos/play/wwdc2025/266/).

### 2.2. Не отображаются системные приложения

**Прямая причина:** `Return Launchpad/AppInfo.swift:87–95` сканирует только `/Applications` и `~/Applications`, причём лишь один уровень. Нет `/System/Applications`, вложенных Utilities и других системных мест размещения. Ошибки чтения скрываются через `try?`.

При проверке этой машины обнаружено:

| Директория | `.app` непосредственно внутри | Сканируется сейчас |
| --- | ---: | --- |
| `/Applications` | 134 | Да |
| `~/Applications` | 3 | Да |
| `/System/Applications` | 46 | Нет |
| `/System/Applications/Utilities` | 19 | Нет |
| `/Applications/Utilities` | 1 | Нет |
| `/System/Library/CoreServices/Applications` | 12 | Нет |

Это число кандидатов в файловой системе, а не обещанное количество иконок после фильтрации. Наличие Calculator, System Settings, Terminal и Finder по системным путям проверено отдельно. Набор и расположение приложений могут отличаться между версиями macOS.

**Решение:**

1. Обходить `/Applications`, `~/Applications`, `/System/Applications`, включая обычные подпапки вроде Utilities. Не заходить внутрь найденных `.app` и других пакетов, чтобы не показывать встроенные helpers.
2. Рассмотреть `/System/Library/CoreServices/Applications` как дополнительный источник. Не сканировать весь CoreServices без фильтра: там много служебных компонентов.
3. Для отдельных пользовательских системных приложений вне этих корней, например Finder, добавить явную политику включения. Разрешать их URL через публичные API `NSWorkspace`, избегая привязки к внутренней структуре конкретного релиза ОС. API разрешения по bundle ID дополняет каталог, но не перечисляет все установленные приложения.
4. Исключать скрытые и фоновые bundles по проверяемой политике. Флаги `LSUIElement` / `LSBackgroundOnly` — сигналы для фильтра, а не универсальная гарантия назначения приложения; предусмотреть исключения.
5. Канонизировать пути, исключать циклы ссылок и дубли. Заранее определить поведение для двух копий одного bundle ID: рекомендуемый вариант первой версии — одна выбранная установка с сохранением пользовательской позиции.
6. Иконку получать через `NSWorkspace.icon(forFile:)` и кэшировать. Отсутствие `CFBundleIconFile` или `.icns` не должно исключать приложение. Для имени использовать локализованные метаданные с fallback на имя файла.
7. Ошибку доступа показывать как ошибку источника, а не как пустой каталог. Проверить подписанную sandbox-сборку отдельно: доступ из терминала не доказывает доступ процесса приложения.

Публичная точка интеграции с приложениями и их иконками: [NSWorkspace](https://developer.apple.com/documentation/appkit/nsworkspace). Отключение sandbox и выдача Full Disk Access не предлагаются как исправление отсутствующих путей.

### 2.3. Папки отсутствуют на уровне модели

`Return Launchpad/AppInfo.swift:11–16` описывает только приложение. `AppManager.apps` — плоский массив, `AppOrderManager.userDefinedOrder` — массив строк. В `ContentView` нет сущности папки, её содержимого, открытия и переименования. Это новая функция, а не скрытая настройка или неисправный обработчик.

**Решение:** ввести отдельную модель раскладки: элементы-приложения и элементы-папки со стабильными ID; порядок корневых элементов и порядок содержимого каждой папки хранить явно. Каталог установленных приложений и пользовательскую раскладку разделить. Папки виртуальные: ничего в `/Applications` не перемещается.

Первый выпуск: один уровень папок, создание наведением на центр другой иконки с выдержкой, добавление в существующую папку, переименование, открытие, извлечение элемента и отмена действия. Вложенные папки отложить. Предлагаемая политика: папка с одним элементом остаётся; пустая удаляется после подтверждённого переноса, с возможностью Undo.

### 2.4. Появление и движение выглядят резкими

**Подтверждено исходниками:**

- `ContentView.swift:256–264`: первый переход явно установлен в `.identity` через `isInitialLoad`. Анимации появления всего окна нет.
- `ContentView.swift:436–442`: окно сразу получает размер экрана через `setFrame(..., display: true)` в `onAppear`.
- `ContentView.swift:445–454`: автопереход при drag меняет страницу без `withAnimation`, хотя кнопки пагинации используют spring.
- `ContentView.swift:349–356`: `ForEach` идентифицирует строки и колонки по позициям. При перестановке меняется содержимое ячеек с прежними ID вместо последовательности самостоятельных элементов.
- `ContentView.swift:377` содержит `matchedGeometryEffect`, но он не заменяет корректную идентичность элементов и модель промежуточной раскладки.
- `AppInfo.swift:12`: UUID генерируется заново при создании `AppInfo`. В пределах текущего массива он сохраняется; проблема возникает при пересканировании и декодировании, когда те же приложения получают новые ID.

**Решение:** подготовка окна до показа; отдельные состояния showing / visible / hiding; переход opacity + небольшой scale; стабильные ID; одна система координат и единая геометрия ячеек. Анимировать конкретное изменение позиции, а не всю загрузку каталога. Глобальный `withAnimation` в `updateFilteredApps()` разделить на действия поиска, обновления каталога и перестановки.

Apple связывает предсказуемое обновление SwiftUI с идентичностью элементов и узкими зависимостями состояния: [Demystify SwiftUI performance](https://developer.apple.com/videos/play/wwdc2023/10160/). Для согласованного движения в SwiftUI и AppKit есть штатная интеграция анимаций: [Unifying your app’s animations](https://developer.apple.com/documentation/swiftui/unifying-your-app-s-animations).

### 2.5. Перетаскивание и страницы

| Причина | Где находится | Последствие |
| --- | --- | --- |
| Нет `dropEntered` / `dropUpdated` у делегата иконки | `ContentView.swift:563–595` | Порядок меняется только на отпускании; живого освобождения места нет |
| Нет отдельного состояния места вставки | `ContentView.swift:343–423` | Исходная ячейка остаётся в сетке с пониженной прозрачностью; собственный визуальный слой drag не управляется |
| Флаг cross-page включается на любом старте | `DragSessionManager.swift:39–51`; `ContentView.swift:345` | Условие использования `stablePageApps` не выполняется в обычной активной сессии |
| Переход возможен только над маленькими стрелками | `ContentView.swift:294–315`; `DragSessionManager.swift:27–28` | Нужно точно попасть в зону и ждать 1,5 секунды; край экрана не работает |
| Таймер ожидания не хранится; таймеры создаются через `scheduledTimer` | `DragSessionManager.swift:97–150` | Сложно гарантировать единственный актуальный callback; режим run loop при native drag нужно проверить отдельно |
| Смещение destination на −1 при движении вправо | `AppOrderManager.swift:382–398` | `0 → 1` оставляет порядок прежним; `0 → 2` ставит элемент в позицию 1 |
| Координаты вычисляются по фильтрованной странице, применяются к полному массиву | `ContentView.swift:54,407–420,579–584` | Во время поиска может переместиться другое приложение |
| Нет общего обработчика завершения/отмены drag | `ContentView.swift:574–593,616–618` | Drop на себя возвращает false до очистки; фон, стрелка, уход из окна и отмена не обеспечивают сброс состояния |
| Нет drop-зоны после последней иконки | `ContentView.swift:354–358` | Нельзя явно положить элемент в свободное место в конце |

Поправка `destination - 1` корректна для контракта «вставить перед исходной целевой ячейкой», но не для «переместить в конечную позицию». Сейчас контракт не выражен, а `testMoveAppChangesOrder` ожидает второй вариант. Поэтому требуется определить семантику операции, а не просто убрать одну строку.

Пример отдельной ошибки поиска: полный список `[A,B,C,D]`, результаты поиска `[B,D]`. Перенос D на B передаёт индексы `1 → 0` в полный список и перемещает B. До внедрения адресации по ID перестановку в поиске следует отключить.

Уточнение к наблюдению пользователя: в текущей ревизии hover над иконкой сам по себе не вызывает перестановку. По коду она происходит на drop; если установленная версия перестраивает сетку уже при наведении, нужно сопоставить её сборку с этой ревизией.

## 3. Рекомендуемое устройство следующей версии

Рекомендация для этого проекта — сохранить SwiftUI для поиска, настроек, папок и общего интерфейса, а жизненный цикл окна и сложную drag-сессию поручить небольшому слою AppKit. Это инженерный выбор по требованиям, а не утверждение, что SwiftUI не способен обеспечить плавную сетку.

| Компонент | Ответственность |
| --- | --- |
| `ApplicationCatalog` | Источники приложений, фильтрация, обновление метаданных, ошибки доступа |
| `IconCache` | Кэш по ID, версии приложения и масштабу; ограничение памяти; приоритет видимых элементов |
| `LayoutStore` | Порядок и папки, проверка инвариантов, миграция, сохранение, Undo |
| `LauncherState` | Поиск, текущая страница, выделение, открытая папка; UI-изменения на MainActor |
| `DragCoordinator` | Единственная drag-сессия, исходный snapshot, предварительное место вставки, таймеры, commit/cancel |
| `LauncherWindowController` | Показ и скрытие, повторное открытие, активный экран, focus, Spaces |

Начать с небольшого прототипа `NSCollectionView` через `NSViewRepresentable`: стабильные item IDs, native dragging session, предварительная перестановка и движение между страницами. Его принимают только после проверки плавности, отмены и переноса на другую страницу. `NSCollectionView` предоставляет точки проверки drop и окончания сессии; поведение папок, предварительного сдвига и краёв всё равно нужно написать. Документация: [validateDrop](https://developer.apple.com/documentation/appkit/nscollectionviewdelegate/collectionview(_:validateDrop:proposedIndexPath:dropOperation:)), [NSDraggingSource](https://developer.apple.com/documentation/appkit/nsdraggingsource).

Альтернатива для прототипа — плоский `ForEach` по ID, собственный SwiftUI `Layout` и управляемый drag overlay. Выбирать по результатам одинакового сценария, без параллельного переписывания всего приложения. Для основного пути AppKit native dragging image должен быть единственным изображением у курсора: не рисовать поверх него второй overlay.

### Хранение и идентичность

Предлагаемая структура, не готовый API:

```text
ApplicationRecord: appID, bundleIdentifier, canonicalURL, displayName, iconVersion
LayoutDocument: schemaVersion, revision, rootItems, folders
LauncherItem: application(appID) | folder(folderID)
Folder: folderID, title, orderedAppIDs
DragSession: sessionID, sourceItemID, originalLayout, previewLayout, target
DropTarget: before(itemID) | after(itemID) | end(containerID) | into(folderID)
```

ID должен переживать пересканирование. Для папки подходит сохраняемый UUID; для приложения требуется стабильное сопоставление с записью каталога и политика дубликатов. Не полагаться одновременно на случайный UUID, equality по URL и persistence по bundle ID, как сейчас.

Сначала мигрировать существующий массив bundle ID в новую раскладку с резервной копией. Сохранять документ с версией схемы атомарно после подтверждённого изменения; настройки вроде темы оставить в `UserDefaults`. Не сохранять TIFF иконок внутри документа раскладки. Отдельная база данных на этом масштабе пока не обязательна.

Убрать необязательные `synchronize()` и сохранение по безусловному таймеру; Apple прямо отмечает, что `synchronize()` не нужен: [UserDefaults.synchronize](https://developer.apple.com/documentation/foundation/userdefaults/synchronize()). Ошибка чтения источника не должна приводить к удалению его элементов из пользовательских папок. Для действительно удалённого приложения определить отдельную политику после успешного полного сканирования.

## 4. Контракт взаимодействия

### Перестановка

1. После начала drag сохранить исходную раскладку, source ID и смещение курсора относительно иконки.
2. Под курсором движется одно изображение; в сетке остаётся место вставки. Геометрия исходной ячейки не исчезает бесконтрольно.
3. По координатам вычислять семантическую цель: перед, после, конец контейнера или внутрь папки. При изменении цели строить preview-раскладку и анимировать соседей.
4. Не записывать предварительные перестановки в постоянное хранилище. Drop выполняет одно подтверждённое изменение и создаёт одно действие Undo.
5. Escape, drop вне цели, потеря окна и системное завершение drag возвращают исходную раскладку, очищают подсветку и отменяют все отложенные действия.

Состояния: `idle → dragging → previewing / pageSwitching / folderHover → committing → idle`; из любой активной фазы возможен `cancel → idle`. Центр иконки предназначен для папки после выдержки; края — для перестановки. Устойчивый порог между этими зонами предотвращает дрожание цели. Поддерживать альтернативное управление с клавиатуры и VoiceOver. Принципы обратной связи и доступности: [Apple HIG: Drag and drop](https://developer.apple.com/design/human-interface-guidelines/drag-and-drop).

### Перенос между страницами

Краевые зоны должны занимать боковые полосы области сетки. Первый предлагаемый диапазон ширины — 48–72 pt. Выдержка перед переходом — 450–600 мс; следующий переход только после завершения анимации и повторного ожидания. Это исходные продуктовые параметры для настройки, не нормы Apple.

Использовать одну отменяемую задачу ожидания с session ID. При выходе из зоны, смене направления, отмене или достижении границы её отменять. Не выполнять файловую работу из обработчика движения. Предусмотреть конец неполной страницы; если продукт допускает пустые страницы, явно хранить их в модели. Для первой версии рекомендуется автоматическая пагинация по порядку без постоянных пустых страниц.

После поворота раскладки из-за изменения размера окна заново рассчитывать цель по ID и координатам, а не использовать старый `page * itemsPerPage + index`. Не уничтожать владельца drag-сессии при переключении страницы.

### Папки

При наведении на центр приложения показывать намерение создать папку через 500–700 мс; при выходе из центральной зоны отменять. Drop создаёт папку и переносит оба элемента одной транзакцией. Наведение на существующую папку может открыть её после выдержки и позволить выбрать внутреннюю позицию.

Escape сначала отменяет drag, затем закрывает папку, затем скрывает лаунчер. Переименование подтверждается Enter, отменяется Escape. В поиске показывать найденные приложения с именем родительской папки; перестановку результатов поиска в первой версии отключить. Все элементы должны оставаться достижимыми с клавиатуры.

### Окно и запуск

Скрытие по Escape и после запуска приложения должно иметь завершение анимации. Использовать `NSWorkspace.openApplication(at:configuration:completionHandler:)`, чтобы обработать ошибку запуска; обновления интерфейса из completion возвращать на MainActor. При ошибке оставить пользователю понятный способ повторить действие. API описан в [документации Apple](https://developer.apple.com/documentation/appkit/nsworkspace/openApplication(at:configuration:completionHandler:)).

Окно показывать на выбранном активном дисплее, проверять Spaces и полноэкранные приложения; не использовать `NSScreen.main!` без fallback. Предлагается обычное управляемое окно без рамки или подходящий `NSPanel`; выбор подтвердить тестами активации и ввода. Поддержать повторный запуск из Dock через обработку reopen. Глобальную горячую клавишу и запуск при входе добавлять отдельным этапом, если они нужны продукту.

## 5. Анимации и библиотеки

Начать со штатных SwiftUI spring/transition и AppKit/Core Animation. Они позволяют анимировать реальные позиции и состояния интерфейса; готовые декоративные эффекты не заменяют drag-координатор. Apple описывает общую модель здесь: [SwiftUI animations](https://developer.apple.com/documentation/swiftui/animations), [Unifying your app’s animations](https://developer.apple.com/documentation/swiftui/unifying-your-app-s-animations).

| Вариант | Поддержка macOS / назначение | Решение для Return Launchpad |
| --- | --- | --- |
| SwiftUI + AppKit / Core Animation | Штатные средства платформы, spring, opacity, transform, управляемые переходы | Основной вариант без новых зависимостей |
| [Motion, b3ll](https://github.com/b3ll/Motion) | Физические пружины и затухание, прерываемые движения; macOS заявлен | Кандидат, если прототип покажет необходимость точного управления скоростью и прерыванием; не готовая сетка |
| [Pow](https://github.com/EmergeTools/Pow) | Набор SwiftUI-эффектов; manifest объявляет macOS 12+ | Только необязательные микроэффекты после основных исправлений; совместимость каждого выбранного эффекта проверить |
| [Lottie](https://github.com/airbnb/lottie-ios) | Проигрывание подготовленных векторных анимаций; manifest объявляет macOS 10.15+ | Подходит для онбординга и иллюстраций; не использовать для перестановки настоящих иконок |

Платформы сверены по текущим manifest: [Motion Package.swift](https://raw.githubusercontent.com/b3ll/Motion/main/Package.swift), [Pow Package.swift](https://raw.githubusercontent.com/EmergeTools/Pow/main/Package.swift), [Lottie Package.swift](https://raw.githubusercontent.com/airbnb/lottie-ios/master/Package.swift). Это движущиеся ветки, а не зафиксированные релизы. У Motion README и manifest расходятся в минимальной версии macOS; для текущего deployment target 15.5 это не блокер. Перед подключением закрепить конкретный релиз, проверить лицензию, зависимости, сборку и стоимость по памяти. В рамках аудита библиотеки не устанавливались и не тестировались внутри приложения.

Предлагаемые стартовые параметры:

| Действие | Начальная настройка |
| --- | --- |
| Появление окна | 180–240 мс, opacity и scale примерно 0.97 → 1 |
| Скрытие | 120–180 мс, затем скрытие окна |
| Сдвиг соседних иконок | Spring с целевым временем успокоения около 180–260 мс, минимальный отскок |
| Переход страницы | 220–300 мс; drag image продолжает следовать курсору |
| Открытие папки | 200–280 мс с сохранением визуальной связи с её иконкой |
| Reduce Motion | Убрать масштабирование, пролёты и пружинный отскок; использовать короткое затухание |

Параметры нужно подобрать на машине пользователя и проверить при 60/120 Гц. Не анимировать курсорное следование с задержкой: пружина предназначена для соседей и завершения переноса. Уважать [accessibilityReduceMotion](https://developer.apple.com/documentation/swiftui/environmentvalues/accessibilityreducemotion); визуальная полировка не должна мешать быстрому запуску.

## 6. Дополнительные дефекты и нативное поведение

- `ContentView.swift:523–539`: callbacks `KeyboardHandler` задаются в `makeNSView`, но не обновляются в `updateNSView`. Они могут работать с устаревшими захваченными значениями страницы и фокуса. Перенести обновление callbacks в `updateNSView` либо coordinator.
- Размер ячейки и расчёт вместимости расходятся: `.frame(height: 120).padding(10)` даёт 140 pt до межстрочного отступа, а расчёт использует 120. Геометрию вынести в один источник, проверить маленький экран и неполную страницу.
- `AppManager.moveApp` логирует `apps[sourceIndex]` до проверки границ нижележащим менеджером. Проверять запрос на границе модели и использовать ID.
- Проверять VoiceOver labels, видимый focus, клавиатурное перемещение в двух измерениях, Enter, Escape и Undo. Размеры мобильных touch targets не следует механически переносить в macOS; реальные цели проверить мышью и трекпадом.
- Размытие оставить через системный материал, обеспечить контраст на светлых и тёмных обоях и режим Reduce Transparency. Новые эффекты Liquid Glass не являются условием исправления и должны иметь fallback для поддерживаемых ОС.

| Этап | Работа | Критерий завершения |
| --- | --- | --- |
| 0. Безопасная база | Изолировать test storage; зафиксировать воспроизведение; добавить измерения; определить контракт move | Тесты не читают/не очищают рабочие настройки; есть baseline холодного и повторного открытия |

Не начинать с добавления библиотеки эффектов: главный риск — несогласованные состояние и геометрия. Начальный технический приоритет: этап 0, затем каталог и жизненный цикл, после этого drag-модель и папки.

### Измерения

Использовать Release на одном выбранном эталонном Mac; фиксировать ОС, модель, дисплей и число приложений. Разделить запуск нового процесса, восстановление с дискового кэша и повторный показ уже работающего процесса. Измерять время первого видимого кадра отдельно от готовности к вводу.

Добавить интервалы signpost: `catalog.scan`, `icons.firstPage`, `layout.load`, `window.present`, `drag.preview`, `layout.commit`. Instruments Time Profiler и SwiftUI instrument помогут отделить блокировки UI от избыточных обновлений: [Optimize SwiftUI performance with Instruments](https://developer.apple.com/videos/play/wwdc2025/306/).

Начальные цели для согласования: повторный показ — первый отклик p95 ≤ 100 мс, завершение перехода ≤ 250 мс; холодный показ с кэшем — доступный для ввода интерфейс p95 ≤ 500 мс. Для плавности ориентироваться на бюджет кадра 16,7 мс при 60 Гц и 8,3 мс при 120 Гц, отдельно следить за редкими длинными кадрами. Показатели собрать минимум на 30 повторах для каждой категории; состояние файлового кэша ОС явно отметить. Проверить каталоги 100/300/1000 уникальных записей, память кэша и отсутствие периодической работы в скрытом состоянии.

### Проверки поведения

| Область | Обязательные сценарии |
| --- | --- |
| Порядок | Первый ↔ последний, сосед справа/слева, конец списка, перенос через строку; точный ожидаемый массив |
| Drag | Drop на себя, фон, вне окна; Escape; потеря активации; быстрый повторный drag |
| Страницы | Перенос вперёд/назад, удержание края, выход и повторный вход в зону, последняя неполная страница |
| Папки | Создание, переименование, внутрь/наружу, пустая папка, Undo, перезапуск после каждого изменения |
| Каталог | Вложенные директории, дубли bundle ID, битый bundle, нет иконки, отказ в доступе, удалённое приложение |
| Persistence | Миграция без потери порядка, повреждённый документ, атомарная запись; ID стабилен после rescan |

| Платформа | macOS 15.5 и целевая macOS 26, масштаб дисплея, два монитора, Spaces, полноэкранное приложение |

Инварианты модели проверять unit-тестами: каждое размещённое приложение находится максимум в одном контейнере, ID не меняются при reorder, cancel сохраняет исходный документ, commit сохраняет именно preview, Undo восстанавливает предыдущий документ. Для UI нужны настоящие pointer-drag сценарии: обычный вызов `moveApp` не проверяет наведение, краевые зоны и отмену.
