# Аудит памяти — 11 сентября 2026

Проверена установленная Release-сборка 3.6.5 (18), ARM64, macOS 26.6.2, каталог из 206 приложений. Короткая проверка заняла несколько минут: запуск, скрытие, три повторных открытия, 16 переключений страниц и скрытие. Раскладка не менялась.

## Измерения

| Состояние | phys_footprint | Пик с запуска | RSS | CPU в покое |
| --- | ---: | ---: | ---: | ---: |
| После запуска и скрытия, серия 12 секунд | 42 МБ | 63 МБ | 170 МиБ | 0,0% |
| После первого прохода всех страниц и скрытия | 33 МБ | 77 МБ | — | — |
| После повторных открытий и проходов, серия 12 секунд | 44 МБ | 81 МБ | 261 МиБ | 0,0% |

Это разные показатели памяти: RSS включает резидентные страницы процесса, phys_footprint показывает учитываемую системой нагрузку памяти процесса. Нельзя обещать, что любой системный монитор покажет ровно 44 МБ. Внутри обеих фоновых серий phys_footprint был постоянным с точностью округления инструмента. После использования интерфейса RSS вырос; один короткий прогон не доказывает, что дальнейшего роста никогда не будет.

## Утечки и ограничения

В исходно запущенной Debug-сборке `leaks` сообщил 288 объектов / 14 400 байт в циклах NSXPCConnection/AppIntents (`com.apple.linkd.autoShortcut` и реестр процессов). Это системные объекты в отчёте; доказательств, что их создаёт ошибка владения в коде лаунчера, не получено.

У Release-сборки анализатор прямо предупредил об ограниченном доступе к памяти защищённого процесса. Он сообщил сначала 20 224, затем 37 184 байта потенциальных утечек, включая небольшие NSArray. Эти результаты нельзя выдавать ни за подтверждённую утечку приложения, ни за нулевые утечки: для атрибуции нужны доступный для отладки процесс и стеки выделения. Объём мал относительно общего потребления, но рост подозрительных объектов остаётся пунктом для последующей проверки.

## Проверка кода

- IconCache держит декодированные иконки всего каталога намеренно. Для 206 иконок RGBA 192×192 это около 29 МиБ исходных пикселей без учёта сжатия и служебных структур. Очистка всего кэша при скрытии вернёт задержки при открытии и перелистывании.
- Окно сохраняется при скрытии, плитки переиспользуются по идентификаторам. Это ограниченное каталогом удержание интерфейса, а не создание нового окна на каждом открытии.
- Постоянного таймера пересканирования нет: проверка необходимости сканирования вызывается при открытии. Отложенная обработка иконок прекращается, когда очередь пуста.
- Завершение внутреннего перетаскивания отменяет отложенную обработку, снимает монитор событий и удаляет превью. Обратные ссылки из обработчиков плиток слабые.
- История отмены ограничена 50 изменениями.
- Возможный крайний случай IconCache: смена каталога во время незавершённого чтения иконки может вернуть устаревший результат обратно в кэш после фильтрации. Это не объясняет рост в обычном простое, но при отдельном изменении механизма обновления стоит добавить отбрасывание результатов старого каталога.

## Вывод

В короткой проверке фоновая нагрузка небольшая: 33–44 МБ phys_footprint, 0,0% CPU на замерах. Мегабайтного непрерывного роста в фоне не обнаружено. Полное отсутствие утечек не доказано; остаются маленькие подозрительные выделения и рост RSS после использования интерфейса. По этим данным нет основания очищать полезный кэш или перестраивать окно при каждом открытии. Код приложения в рамках аудита не менялся.

Повторение замера: `footprint -p PID --sample 2 --sample-duration 12 --noCategories`, `ps -p PID -o pid,rss,%cpu,etime`, `leaks PID`. Для проверки длительной тенденции сравнивать одинаковые состояния после прогрева, отдельно от пика анимаций; анализировать подозрительные объекты в Debug со стеками выделения.
